# Metrics & Calculations

How every number in the Claude Code Visibility dashboard is derived.

---

## Data Source

Claude Code writes a JSONL file for every session at:

```
~/.claude/projects/<project-dir>/<session-id>.jsonl
```

Each line is a JSON record with a `type` field. Token and cost data comes exclusively from records where `type == "assistant"` — specifically from the `message.usage` object that Anthropic returns with every API response.

```json
{
  "type": "assistant",
  "message": {
    "model": "claude-sonnet-4-6",
    "stop_reason": "tool_use",
    "usage": {
      "input_tokens": 1200,
      "output_tokens": 340,
      "cache_read_input_tokens": 8800,
      "cache_creation_input_tokens": 9100
    },
    "content": [...]
  }
}
```

No estimation is involved — these are the exact values returned by the Anthropic API.

---

## Token Counts

For each assistant message, four token fields are extracted and accumulated per session:

| Field in JSONL                    | Dashboard label  | Description                                      |
|-----------------------------------|------------------|--------------------------------------------------|
| `usage.input_tokens`              | Input Tokens     | Fresh tokens sent as input (not from cache)      |
| `usage.output_tokens`             | Output Tokens    | Tokens generated by the model                   |
| `usage.cache_read_input_tokens`   | Cache Read       | Tokens served from the prompt cache (cheap)     |
| `usage.cache_creation_input_tokens` | Cache Creation | Tokens written into the prompt cache (one-time) |

```python
# parsers.py:214-217
session["tokens"]["input"]        += usage.get("input_tokens", 0)
session["tokens"]["output"]       += usage.get("output_tokens", 0)
session["tokens"]["cache_read"]   += usage.get("cache_read_input_tokens", 0)
session["tokens"]["cache_creation"] += usage.get("cache_creation_input_tokens", 0)
```

Session totals are summed across all sessions for project-level and overview-level figures.

## Cost

### Pricing table

Costs are per million tokens ($/M):

| Model              | Input  | Output  | Cache Write | Cache Read |
|--------------------|--------|---------|-------------|------------|
| claude-sonnet-4-6  | $3.00  | $15.00  | $3.75       | $0.30      |
| claude-haiku-4-5   | $0.80  | $4.00   | $1.00       | $0.08      |
| claude-opus-4-6/7  | $15.00 | $75.00  | $18.75      | $1.50      |

If the model is unknown or unrecognised, Sonnet 4.6 pricing is used as the default.

### Formula

```python
# parsers.py:42-49
cost = (input_tokens        * price["input"]       / 1_000_000)
     + (output_tokens       * price["output"]      / 1_000_000)
     + (cache_creation_tokens * price["cache_write"] / 1_000_000)
     + (cache_read_tokens   * price["cache_read"]  / 1_000_000)
```

Cost is computed per assistant message and accumulated across the session. The model is read per-message, so sessions that switch models mid-way are priced correctly.

## Cache Efficiency

Cache efficiency measures what percentage of all cache-related tokens were **served from cache** (reads) rather than **written to cache** (writes).

```python
# parsers.py:417-418
cache_total      = cache_read + cache_creation
cache_efficiency = (cache_read / cache_total) * 100   # expressed as %
```

**Why it matters:** Cache reads cost ~10x less than cache writes (e.g. $0.30 vs $3.75/M for Sonnet). A high cache efficiency means most context is being reused, significantly reducing cost.

- **50%** — half the cached tokens are being reused
- **80%+** — strong reuse, context window is stable across turns
- **<20%** — context changes frequently, cache is not helping much

## Agentic Ratio

The agentic ratio is derived from `stop_reason` values on assistant messages.

Claude stops for one of two primary reasons:
- `tool_use` — Claude invoked a tool and is waiting for the result (autonomous action)
- `end_turn` — Claude finished its response (conversational reply)

```python
# parsers.py:220-222
stop_reason = msg.get("stop_reason", "")
session["stop_reasons"][stop_reason] += 1

# Overview.tsx:403-405
agentic_ratio = tool_use_count / end_turn_count
```

A ratio of **2.6:1** means Claude stopped to take an action 2.6 times for every conversational reply — indicating predominantly autonomous, agentic work rather than Q&A.

## Thinking Blocks

A thinking block is a `content` item of `type == "thinking"` inside an assistant message. These appear when Claude uses extended thinking (deep multi-step reasoning).

```python
# parsers.py:239-240
if ctype == "thinking":
    session["thinking_blocks"] += 1
```

Counted per content block, accumulated per session, then summed at overview level.

---

## File Edits

File edits are counted from `file-history-snapshot` records in the JSONL. These are written by Claude Code whenever it backs up a file before editing it.

```python
# parsers.py:177-180
if rtype == "file-history-snapshot":
    snap = rec.get("snapshot", {})
    edits = len(snap.get("trackedFileBackups", {}))
    session["file_edits"] += edits
```

Each key in `trackedFileBackups` represents one file that was modified in that session checkpoint.

---

## Tool Calls

Every `tool_use` content block in an assistant message is recorded as a tool call:

```python
# parsers.py:248-251
elif ctype == "tool_use":
    name = content.get("name", "unknown")
    session["tool_calls"].append({"name": name, "ts": ts})
```

Tools are classified as **builtin** (standard Claude Code tools like `Bash`, `Read`, `Edit`) or **MCP** (anything else). MCP tool names follow the pattern `mcp__<server>__<tool>` and are split for display.

---

## Web Searches & Web Fetches

These come from `usage.server_tool_use` inside assistant messages — a separate usage object Anthropic provides for server-side tools:

```python
# parsers.py:224-226
server_tools = usage.get("server_tool_use", {})
session["web_searches"] += server_tools.get("web_search_requests", 0)
session["web_fetches"]  += server_tools.get("web_fetch_requests", 0)
```

## Model-Level Token Distribution

When a session uses multiple models, token and cost figures are split evenly across models (1/N share per model):

```python
# parsers.py:680-688
share = 1 / len(models)
ms["tokens_in"] += int(s["tokens"]["input"] * share)
ms["cost"]      += s["cost"] * share
```

This is an approximation — the actual per-model split is not recorded in the JSONL at session level.

---

## Project-Level Aggregation

All per-session values are summed per project directory. Cache efficiency is recalculated at the project level using the same formula as the overview.

---

## Config & Infrastructure

Config data is sourced from:

| Data                  | Source file                                      |
|-----------------------|--------------------------------------------------|
| Global MCP servers    | `~/.claude/backups/.claude.json.backup.*`        |
| Per-project MCP       | Same backup file, under `projects[path].mcpServers` |
| Allowed tools         | `projects[path].allowedTools`                   |
| Installed plugins     | `~/.claude/plugins/marketplaces/`               |
| Skill usage           | `claude_json["skillUsage"]`                     |
| Live sessions         | `~/.claude/sessions/*.json` + `os.kill(pid, 0)` to check if alive |

---

## What Is Not Estimated

Every metric in this dashboard is derived directly from data written by Claude Code or returned by the Anthropic API. The only approximation is the per-model token split in multi-model sessions.
